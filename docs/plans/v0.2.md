# ternly v0.2 — frontier-grade results at minimum cost, with a best-in-class UI

Read `docs/DEV_PROMPT.md` (working rules), `CHANGELOG.md`, ADRs 012–016 and the open issues
first. All working rules still apply:
- ground every claim
- write an ADR per decision
- measure before you claim
- break each guard to prove its test
- run `bench/run.sh e2e` before each review
- push to a branch, open a PR, and merge only when CI is green

Where a goal below cannot be met literally, say so, and deliver the strongest measurable version.

## Non-negotiables: integrate, never regress
v0.2 extends v0.1 and must not replace it. Everything built so far stays and keeps working.

1. **Baseline before any change.** Tag the starting point. Then commit `bench/baseline.json` with
   the current numbers for every measured path:
   - startup and resume
   - event append and memory retrieval
   - graph build, load and incremental update
   - grep and the file tools
   - render and keystroke latency
   - binary size and peak RSS
   - e2e pass rates and per-model susceptibility

   Every phase reports against it.
2. **Performance gate in CI.** Run benchmarks with repeated counts and compare them with benchstat.
   Fail a PR on a statistically significant regression beyond the budget (default 5%; ADR to
   change). Hot paths get pprof CPU and allocation profiles and allocation budgets; a new feature
   pays its own cost.
3. **No silent test erosion.** Existing tests, the scripted-adversary suite and the e2e manifest
   stay green. Don't delete, skip, weaken or re-threshold any test without an ADR. Coverage may not
   drop.
4. **Extend; don't rewrite.**
   - Put new routing, provider bridges and UI behind interfaces and feature flags.
   - The old path stays the default until the new one is proven equal or better on the eval suite
     and benchmarks.
   - Then flip the default, and remove the old path one release later.
5. **User data is sacred.** Session logs, memory, config, the graph and checkpoint stores, and
   plugin state are versioned formats. Every format change needs:
   - a forward migration
   - tests against committed v0.1 fixtures
   - a rollback story

   An upgrade never loses or corrupts user data, and a downgrade fails safely.
6. **Security moves with every change.** Every new surface (CLI bridges, image paste, the
   improvement loop, new auth) updates `docs/threat-model.md`. It also gets scripted-adversary
   tests and a security-review pass before merge. Add `govulncheck` and `staticcheck` to CI.
7. **When goals genuinely conflict,** this is the order:
   1. security
   2. correctness and user data
   3. output quality
   4. performance
   5. cost
   6. development speed

   Record every such trade-off in an ADR. "No compromise" means no *silent* compromise.

## Production-quality definition of done (every PR)
- tests for success and failure paths; new guards proven by breaking them
- no regression against `bench/baseline.json`; profiles attached for hot-path changes
- security review done; threat model updated if the attack surface changed
- data formats migrated with fixture tests; config backward compatible
- clear, actionable errors; no panics reach the user (recover, then a local crash report)
- docs, CHANGELOG and ADR updated; the UI keeps accessibility and no-colour modes
- `go vet`, `staticcheck`, `govulncheck`, race tests and fuzz smoke runs pass; real-model e2e
  before each phase review

## Faster development without lower quality
- **Parallel tracks in separate git worktrees, each with its own PR.** After Phase A:
  - Track 1: B → C → D → E. These are dependent: they share the eval suite.
  - Track 2: F (UI). Mostly independent; it consumes routing and status data through interfaces
    defined at the start.

  Agree the interface contracts between tracks in an ADR first. Merge often to avoid drift.
- **Tiered feedback:**
  - fast unit tests (`-short`, under 60 s) on every change
  - full race, integration and adversary suites in CI
  - `bench/run.sh e2e quick` while iterating
  - full e2e before review
  - nightly fuzzing
- **Small PRs.** Each one shippable. Patch releases (v0.1.x) whenever a phase is ready, not
  big-bang releases.
- **Dogfood.** Use ternly, with cloud models, for part of each phase. Report what it exposed.

## Phase A — fix model selection first (bug)
Symptom: I'm signed in to Ollama with cloud access, yet ternly defaults to the local
`qwen3.6:latest`. That model is older, and on this machine it runs mostly on CPU, taking up to
30 minutes per task.

1. **Root cause.** Find it before changing anything. Likely factors:
   - the router counts local models as cost 0
   - qwen's measured tier is T3
   - nothing accounts for latency or throughput
   - subscription cloud models are treated as "quota-priced", so they lose on price

   Confirm or refute each with evidence.
2. **New cost model.** Route on expected cost to finish the task successfully, not on token price
   alone:
   - token cost (pay-per-token)
   - marginal subscription cost: prepaid quota is close to free until the limit, and then it isn't
   - the user's waiting time: measure each model's real tokens/sec and time to first token on
     this machine
   - the probability of success at the task's difficulty, from the eval data

   A slow local model must not win just because it's free.
3. **Hardware awareness.** Detect whether a local model runs on GPU or CPU (Ollama reports this),
   and VRAM/RAM headroom.
4. **"Latest and greatest" means best measured, not newest.**
   - New models: use recency and the provider's family position as a prior, run the eval suite on
     them automatically in the background, and then route on measured results.
   - New releases: when a new cloud model appears, evaluate it within the day, using a small fixed
     budget.
   - Visibility: `/models` shows why each model ranks where it does.

## Phase B — connect to every source I'm entitled to, automatically
Goal: zero-config access to Ollama (local and cloud), my Claude subscription, my ChatGPT/Codex
subscription, and API keys if present. I prefer keyless setups.

1. **Terms of service first.** Before building anything, verify each provider's current terms and
   official docs on whether third-party tools may use subscription sign-in. Do not implement any
   auth path a provider prohibits or doesn't officially support, even if it technically works.
   Record what you found, with links and dates, in the ADR.
2. **Official CLI bridges.** Where direct third-party use of a subscription isn't permitted, but the
   provider's own CLI is (e.g. `claude` and `codex`, if installed and signed in), add a bridge
   provider. It drives the official CLI in its headless or JSON mode as a backend. The bridge must
   respect each CLI's own permission and sandbox model, map tool use safely, report
   cost/quota where available, and degrade cleanly when the CLI isn't installed or isn't signed in.
3. **Ollama.** Use the signed-in daemon for both local and cloud models. Detect subscription tier
   and quota from official signals only. Never scrape anything.
4. **Discovery.** All of the above is discovered at startup with no prompts. `/doctor` and `/models`
   show what's connected, how, and what it costs.

## Phase C — frontier-level quality from the cheapest sufficient model
Target: on our eval suite, results close to the best frontier model at a fraction of the cost.
Measure the gap; don't assert it.

1. **Benchmark first.** Build a task suite from this repo and 3–4 public repos (Go, Python, TS,
   Rust). Each task gets a hidden test oracle. Record each model's pass@1, cost and time. Report
   ternly-routed results against the single best frontier model, per task class.
2. **Proven levers.** Add these in order, keeping each only if it measurably helps:
   - strong-model planning with cheap-model execution (`/architect` generalised)
   - tests or compiler as the judge, with best-of-n only when a task is hard and n is small
   - escalation when verification fails
   - retrieval from the graph and memory instead of reading whole files
   - structured outputs and tool schemas
3. **Reproducibility.** Bit-identical output across cloud providers isn't achievable (batching and
   mixture-of-experts make it nondeterministic). Aim for *outcome* determinism instead:
   - pin temperature/seed where supported
   - version every prompt
   - cache responses for identical requests
   - let verification gates decide success

   Measure it by running the same task 5 times and reporting outcome agreement and diff similarity.

## Phase D — spend fewer tokens without losing quality
1. **Terse by default.** No narration of thinking, no restating files or plans, short final
   summaries. Reasoning budgets come from routing, and per-model calibration replaces the guesses
   in ADR 015.
2. **Quality is a hard constraint.** Tests, verification coverage, docs and lint gates never relax
   to save tokens. A token-saving change ships only if the quality metrics on the eval suite are
   unchanged or better. Report quality and tokens side by side.
3. **Metric.** Track tokens and cost per *successful* task, not per request.

## Phase E — results that improve over time, safely
1. **Learn from local outcome data only.** Sources: verification pass/fail, escalations, accepted
   vs reverted edits, user corrections, suggestion outcomes. Nothing leaves the machine.
2. **Offline improvement loop.** Generate candidate changes to prompts, routing weights and
   per-model reasoning settings. Evaluate them on the suite and promote only improvements that are
   no worse on quality, better on cost or quality, and reproducible across runs. Every change is
   versioned with automatic rollback on regression. ternly never rewrites its own behaviour in a
   live session, and promotions need my approval (`/improve review`).
3. **Report.** `/stats` shows the trend: success rate, tokens per success, cost per success and
   time per success, per task class.

## Phase F — the best terminal UI available as of October 2026
"Best" is subjective, so make it measurable.

1. **Survey and rubric.** Survey today's leading coding-agent TUIs: Claude Code, Codex CLI,
   Gemini CLI, Crush, OpenCode, and any others you can verify are current. Build a rubric covering:
   - responsiveness
   - information density without clutter
   - discoverability
   - diff and review experience
   - error clarity
   - accessibility
   - terminal compatibility

   Score each harness against it with recorded evidence, then set ternly's targets above the best
   score on each line.
2. **Features to evaluate and build where they score:**
   - syntax-highlighted inline and side-by-side diffs with per-hunk accept/reject
   - collapsible tool output
   - a live plan/todo panel
   - a context, cost and quota meter
   - a session sidebar
   - a Ctrl+K command palette
   - fuzzy `@` file picker
   - model and routing explanation on demand
   - themes, including GNOME light/dark
   - optional mouse support
   - image paste where the terminal supports it
3. **Performance budgets.** Measure each in CI with golden or teatest tests:
   - keystroke-to-render under 16 ms
   - no flicker
   - ~0% CPU when idle
   - startup under 100 ms
   - smooth with 10k-line transcripts (virtualised rendering)
4. **Compatibility.** Test on kitty, Ghostty, WezTerm, Alacritty, GNOME Terminal, tmux and SSH.
   Provide reduced-motion, no-colour and screen-reader-friendly modes.
5. **Proof.** Record the same 3 tasks in ternly and the two best-scoring harnesses, and present
   the rubric scores with the recordings.
